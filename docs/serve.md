# Interactive sessions and inference serving

Beyond one-shot `run`, saladfingers has two long-lived modes, both driven by the
in-container agent's HTTP API (`sf-agent serve`) through the SaladCloud gateway. Both
self-stop when idle so a forgotten box never bills indefinitely.

## `session` — an interactive GPU dev box

```sh
saladfingers session create --image REF --gpu-class "RTX 3060 (8 GB)" \
  --deadman 15m --max-duration 4h --name dev
saladfingers session exec dev -- nvidia-smi
saladfingers session cp ./data.bin dev:/work/data.bin     # upload
saladfingers session cp dev:/work/out.bin ./out.bin       # download
saladfingers session logs dev                             # container stdout
saladfingers session ls
saladfingers session stop dev        # billing ends
saladfingers session rm dev          # delete the group
```

- The gateway is created with `auth=true`, so requests carry both the Salad key (for
  the gateway) and a per-session bearer token (for the agent). The token is generated by
  the CLI and stored only in local run state; it never enters the repo.
- `exec` streams merged stdout/stderr and **propagates the remote command's exit code**,
  so `session exec dev -- cargo test` works in CI.
- `cp` moves files in resumable 32 MiB chunks (sha256-verified on upload); a re-run
  resumes from what the agent already holds / what is already on local disk.
- **Deadman**: the agent self-exits after `--deadman` of no authenticated requests and
  no running exec. **Max-duration**: an unconditional cap. Self-exit alone does NOT stop
  billing — the platform relaunches the container on every exit regardless of restart
  policy (see `docs/empirical.md` E1/E2/E4) — so `session create` also spawns a detached
  **reaper** that deletes the group once the agent's `boot_id` changes (the box
  relaunched and lost all session state) or the session's budget elapses. `session rm`
  remains the interactive path; `gc` is the backstop.

Concurrency: up to 4 execs at once (a 5th returns `409`). Each exec's output is retained
in an 8 MiB ring; `output` long-polls (waits ≤ 30 s) and reports `truncated` if the ring
evicted bytes you had not read yet.

## `serve` — an inference service behind the gateway

```sh
saladfingers serve up --image REF --gpu-class rtx4090 --app-port 8080 \
  -- infurer qwen36-serve --addr 127.0.0.1:8080
saladfingers serve status  NAME
saladfingers serve autostop NAME --idle-timeout 30m      # foreground watchdog
saladfingers serve down NAME       # stop (billing ends)
saladfingers serve resume NAME     # start again (new node; the app reloads)
saladfingers serve rm NAME
```

`serve up` deploys a group whose agent runs `sf-agent serve --proxy`: it supervises the
app on loopback and reverse-proxies all non-`/sf/*` gateway traffic to it, **streaming
responses** so SSE / token streams pass through.

- The gateway uses **`auth=false`** — end users reach the app with no Salad key; the app
  enforces its own auth (e.g. an API-key header it checks itself).
- `/sf/v1/ready` (unauthenticated) reports whether the app is accepting connections yet;
  `serve up` polls it before declaring the service ready (the app may still be loading
  weights). `/sf/v1/idle` (bearer-guarded) reports idle seconds.
- `serve autostop` is a foreground watchdog: it polls `/sf/v1/idle` and stops the group
  once it has been idle past `--idle-timeout`. Combine with `--max-duration` on `up` for
  a hard ceiling. If the app process dies, the proxy exits and the platform relaunches
  the container (E1/E2), restarting the app — the service self-heals rather than stops.
  Billing ends only via `serve down`/`rm`, the autostop watchdog, or `gc`.

Because SaladCloud gives no per-instance routing, one service = one single-replica group;
scale by bringing up several.

## Gateway limits (why it works this way)

The SaladCloud gateway caps requests at **100 s** and **1 GB**. So: exec output is
long-polled in ≤ 30 s waits, files move in bounded chunks, and the proxy streams
responses rather than buffering them. WebSockets require `auth=false` and are avoided in
v1 in favour of long-poll. Bind the app to loopback (`127.0.0.1:<app-port>`); the agent
owns the IPv6 `[::]` gateway socket.
